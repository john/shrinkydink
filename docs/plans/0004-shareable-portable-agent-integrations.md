# Plan: Shareable and portable agent integrations

Source brief: docs/features/0004-shareable-portable-agent-integrations.md
Status: implemented
Planned against commit: 3dc041ae40916be824e5c212ae8e2087265c35f7
Base commit: 1cc069f4135266331ea0ccec4f2642e978c8ebb6

## Outcome

Move Shrinkydink's team-shared Claude integration from ignored local settings into committed project settings, add a conservative native-deny layer for secret paths without translating broader `.agentsignore` semantics, make Claude and Codex hook launchers repository-root-safe on POSIX and native Windows, validate every generated client configuration before it reaches the transactional write set, and make audit output explicit about shared files, local preservation, and client activation steps.

## Scope

### In scope

- Generate and structurally merge committed `.claude/settings.json` with the Shrinkydink `PreToolUse` hook, the optional context status line, and a narrowly allowlisted set of Claude native `Read`/`Edit` deny rules for high-confidence secret paths.
- Stop depending on `.claude/settings.local.json` for shared enforcement. Inspect it only to identify exact Shrinkydink-owned hook/status entries, preserve all personal and unrelated content, migrate only signatures that can be recognized safely, and report entries that require manual cleanup or composition.
- Keep `.claude/settings.local.json` ignored and local; do not create it on a fresh apply merely to activate Shrinkydink.
- Preserve unrelated Claude hooks, permissions, settings, and status-line selections through structural merges. Preserve non-Shrinkydink status lines and report the optional manual composition step instead of replacing them.
- Keep Codex hooks and TUI configuration in committed `.codex/hooks.json` and `.codex/config.toml`, preserving the existing inline-hooks fallback and all unrelated values.
- Replace current working-directory-relative Windows hook commands with a tested native-Windows root-resolution strategy; retain root-safe POSIX commands and Claude's documented project-root placeholder.
- Parse and validate generated Claude JSON, Codex hook JSON, and Codex TOML before any `Change` is admitted to the transactional apply set.
- Add versioned, synthetic integration fixtures for empty configuration, unrelated configuration, recognized Shrinkydink local configuration, nested invocation, and Windows command rendering/path resolution.
- Extend text and JSON audit reports so shared/committed artifacts, local/ignored artifacts, preservation or migration state, and Claude/Codex activation or trust steps are distinct.
- Update generated instruction text and platform/configuration documentation to describe committed Claude settings, native-deny limits, root resolution, trust review, restart/reload behavior, and manual smoke tests.

### Out of scope

- User-global Claude or Codex settings, managed enterprise policy, client trust prompts, OS sandboxing, secret-management systems, or automatic approval of project hooks.
- Additional agent clients, packaging Shrinkydink as a Claude or Codex plugin, or changing the existing `.agentsignore` matching language and guard decisions.
- Translating arbitrary `.agentsignore` patterns, negations, dependency/cache exclusions, generated-output rules, or user-authored patterns into native Claude permissions.
- Guaranteeing enforcement for direct attachments, hosted tools, arbitrary subprocesses, or client surfaces that do not run project hooks.
- Claiming native-Windows client execution from POSIX-only automated tests; this feature adds deterministic rendering/path-resolution coverage plus documented manual client smoke tests.

## Assumptions and decisions

- **D-1 — Committed Claude project settings become authoritative for shared behavior.** `scripts/shrinkydink.py` will plan `.claude/settings.json` even when no local settings file exists. The shared file owns the generated `PreToolUse` hook, safe native denies, and the Shrinkydink status-line command when that scalar is free. `.claude/settings.local.json` remains a personal override surface and is never required on a fresh clone.
- **D-2 — Local migration is signature-based and deliberately conservative.** Recognize only the exact current/legacy Shrinkydink command paths and canonical status-line object. Remove those entries only when the surrounding JSON can be rewritten without reformatting or semantically changing unrelated content; otherwise leave the complete local file byte-for-byte unchanged and emit a manual-migration warning. Never infer ownership from a generic matcher, `python3` command, `$schema`, `respectGitignore`, file location, or status-line shape alone. If removing the last Shrinkydink-owned member would leave an empty managed container, remove only that now-empty container and its necessary JSON delimiter; never delete the local file automatically.
- **D-3 — Native denies use an explicit safe subset, not an `.agentsignore` translator.** Generate only project-scoped Claude `Read` and `Edit` deny rules for static, high-confidence secret defaults whose meaning is representable by Claude permission rules (the exact `.env` filename and private-key/certificate extensions such as `*.pem`, `*.key`, `*.p12`, and `*.pfx`). Do not translate `.env.*`, because the generated `.agentsignore` block re-includes example/template variants, and do not translate any user rule, negation, directory/cache/build rule, configured-path override, or pattern requiring precedence. The hook remains the sole evaluator of full `.agentsignore` ordering and negation semantics.
- **D-4 — Use each client's documented root mechanism.** Render Claude command hooks in exec form with `python3` plus an `args` entry rooted at `${CLAUDE_PROJECT_DIR}` so paths with spaces and nested starts do not rely on shell tokenization. Keep Codex POSIX commands rooted with `git rev-parse --show-toplevel`. Render `commandWindows`/`command_windows` through an explicit PowerShell root-discovery helper expression that resolves `git rev-parse --show-toplevel`, joins the installed helper path, and invokes `py -3`; do not rely on `.agent-tools/...` relative to session `cwd`. Centralize command rendering so JSON and inline TOML cannot drift.
- **D-5 — Validation is structural and dependency-free.** Add focused validators for the generated Claude settings and Codex hook objects (top-level object, permission arrays, event/matcher/handler shapes, command/args/platform fields, and expected managed signatures), then serialize and parse the result again. Continue using `tomllib` to validate existing and generated Codex TOML when available; on older Python, retain the current warning but still validate generated managed fragments before insertion. Pin the released-documentation URLs, Codex generated-schema URLs, reviewed date, and supported subset in fixture documentation rather than adding a runtime JSON-schema dependency.
- **D-6 — Status lines remain user choices.** Add the Shrinkydink Claude status line only when the committed project setting is absent or already recognized as Shrinkydink-managed. A non-Shrinkydink shared or local Claude status line is preserved, and audit output explains that local precedence may hide the shared status line and gives a manual composition option. Retain Codex's existing preserve-and-warn behavior for a non-Shrinkydink `tui.status_line`.
- **D-7 — Audit output gains explicit integration metadata.** Extend planned-change/report data with a stable treatment such as `shared-commit` or `local-ignore`, plus an integration/activation status. Text output groups or labels these states; JSON output exposes machine-readable fields. Report Claude project-settings reload or `/status` verification, Codex project/hook trust and `/hooks` review, and restart only where the relevant current client requires it. Do not report local-file contents.
- **D-8 — Tests model foreign platforms without overstating them.** Fixture-driven tests will materialize repositories under temporary paths, run planning/apply/check twice, execute installed helpers from root and a nested POSIX directory, and assert rendered native-Windows commands/root joins without requiring Claude, Codex, PowerShell, or Windows in CI. The release checklist will retain one manual smoke test per supported client/platform combination required by the brief.
- **D-9 — Preserve unrelated work and establish a fresh run base.** Planning occurred on `feat/0003-gitignore-conformant-agentsignore-semantics` at `3dc041a`, while the live remote default branch is `main` and no feature-0004 branch or pull request exists. The worktree contains user-owned untracked `.agents/`, `.claude/`, and this feature brief. A metadata-only check found no `.claude/settings.json` and did find an ignored `.claude/settings.local.json`; its contents were not read. `run` must fetch the current default branch, establish and record its base through the feature workflow, and preserve all of those paths. In particular, it must not inspect or overwrite the ignored local settings currently under `.claude/` merely because they exist in this planning worktree.

## Planning-time implementation findings

- `scripts/shrinkydink.py::build_plan` currently targets only `.claude/settings.local.json`; `plan_claude_settings` adds the hook, `respectGitignore`, and status line there, and new local files receive mode `0600`. This is the direct cause of AC-1/AC-2 drift and must be split into shared planning plus optional conservative local migration.
- `scripts/shrinkydink.py::plan_codex_hooks_json` and `codex_inline_hook_body` already use a Git-root expression for POSIX, but their Windows commands are `py -3 ".agent-tools\\..."`, which depends on the session working directory. Existing managed handlers are detected by script-name substring and skipped rather than refreshed, so an explicit recognized-handler upsert is needed to migrate old commands idempotently.
- `append_hook` preserves unrelated matcher groups and handlers but only searches the `command` scalar. It must compare normalized managed signatures across `command`, `args`, and Windows overrides, replace exactly one recognized Shrinkydink handler in place, append when absent, and conflict or warn rather than guessing when ownership is ambiguous.
- `load_json_object` protects malformed/non-object JSON, and `plan_codex_config` validates TOML, but generated Claude/Codex JSON receives no client-shape validation beyond successful serialization. Validation must happen inside planning, before `apply_changes` stages any destination, so one invalid generated artifact aborts the whole transaction.
- Current audit output lists paths and generic warnings but has no first-class version-control treatment or activation state. `.claude/settings.json`, `.codex/*`, and runtime helpers should be visibly shared/committed; a present `.claude/settings.local.json` should be visibly local/ignored and preserved or migrated; client-specific trust/reload instructions should not be conflated with configuration conflicts.
- Claude's current public settings and hooks documentation identifies `.claude/settings.json` as team-shareable project scope, `.claude/settings.local.json` as personal/local scope, merges hooks across scopes, gives local settings higher scalar precedence, and recommends `${CLAUDE_PROJECT_DIR}` plus exec-form arguments for project scripts. Its permission reference confirms that only `Read` and `Edit` path rules participate in file permission checks and that deny rules merge across scopes. Sources reviewed 2026-08-03: `https://code.claude.com/docs/en/settings`, `https://code.claude.com/docs/en/hooks`, and `https://code.claude.com/docs/en/permissions`.
- The current Codex manual says project `.codex` layers load only for trusted projects; matching hooks from multiple sources all run; a layer containing both `hooks.json` and inline hooks is merged with a startup warning; non-managed hook definitions are hash-reviewed; commands run with the session `cwd`; `commandWindows`/`command_windows` is the Windows override; and repo-local hooks should resolve from the Git root. Sources reviewed 2026-08-03: `https://developers.openai.com/codex/config-advanced#hooks`, `https://developers.openai.com/codex/config-basic#configuration-precedence`, and the generated hook schemas linked from `tests/fixtures/hooks/README.md`.
- The repository has no package manifest or third-party runtime dependency. Existing verification uses Python `unittest`, subprocess fixtures, direct JSON parsing, optional standard-library `tomllib`, apply/check idempotence, and byte comparisons between canonical runtime assets and committed dogfood copies. The feature should preserve that Python-standard-library-only architecture.

## Risks and follow-ups

- **Claude local JSON cannot always be edited byte-safely.** Formatting, duplicate keys, comments from nonstandard tooling, or user-modified managed objects can make ownership or a surgical rewrite ambiguous. D-2 intentionally prefers an unchanged duplicate hook plus a visible manual cleanup warning over damaging personal settings.
- **Deny semantics are stronger than ignore semantics.** Claude deny rules merge across scopes and cannot be undone by a later `.agentsignore` negation. Keeping the generated native subset explicit and excluding `.env.*` prevents known template/example false positives; future additions require their own representability review and fixtures.
- **Cross-scope hooks can run more than once during migration.** If a legacy local Shrinkydink hook cannot be migrated safely, Claude will merge it with the new project hook. The audit must say that shared enforcement is active and that the recognized-looking local duplicate needs manual removal; it must never silently delete an ambiguous entry.
- **Status-line precedence is scalar and client-specific.** A preserved local Claude status line can hide the committed one, and an existing Codex line may omit `context-remaining`. Treat this as optional presentation/manual composition, not an enforcement failure.
- **Windows quoting is fragile.** Paths with spaces, backslashes, PowerShell expression quoting, Python launcher availability, Git worktrees, and nested starts all need renderer fixtures. POSIX CI proves string construction and root logic, not a real native-Windows client; the manual smoke test remains a release gate or named follow-up.
- **Current schemas can lead releases.** Codex `main` generated schemas may contain unreleased fields, while SchemaStore can lag Claude releases. Tests should pin the reviewed sources and validate only the released subset Shrinkydink emits, with product documentation taking precedence when they differ.
- **Trust and activation are not automatable policy.** A committed project hook can still be skipped by Codex until the project and exact hook hash are trusted, and organizations can disable project hooks. Claude project settings may be subject to workspace trust or managed-only policy. Audit output must explain these states without claiming successful enforcement before client confirmation.
- **Report schema expansion may affect consumers.** Additive JSON fields are preferable to renaming existing keys; retain existing `changes`, `warnings`, modes, and exit codes so CI users do not break.
- **The planning worktree is not the run base.** Live `origin/main` is ahead of the local tracking ref and the current branch contains feature-0003 work. `run` must follow the feature Git workflow, fetch, choose the correct current main base, and isolate feature 0004 without cleaning the untracked brief/skill directories.

# Plan: Conservative defaults, actionable diagnostics, and user documentation

Source brief: docs/features/0005-conservative-defaults-diagnostics-and-documentation.md
Status: implemented
Planned against commit: 971518e3f3d44105799ee10704c4bcb5a00ed48c
Base commit: 971518e3f3d44105799ee10704c4bcb5a00ed48c

## Outcome

Make Shrinkydink's automatic ignore policy narrow and explainable, move ambiguous tracked paths into metadata-only recommendations, give tracked secret-like filenames a distinct high-severity warning, expose additive and stable text/JSON report sections for CI, and replace the placeholder root README with accurate user documentation for all behavior delivered through features 0001-0005.

## Scope

### In scope

- Represent generated `.gitignore` and configured `.agentsignore` rules as classified high-confidence or ecosystem-specific rule groups with a reason for each group.
- Reduce the no-ecosystem `.agentsignore` block to version-control internals, local agent state, and the existing conservative secret defaults and template negations. Move dependency stores, language caches, compiled products, and build output under the ecosystem that justifies them.
- Stop automatically adding broad `vendor/`, `out/`, database, archive, generic binary, and source-map rules without a qualifying ecosystem. Permit `build/` only for the current Node, Python, and Java detections; `*.map` only for Node; and Java package/class outputs only for Java. Keep Ruby's precise `vendor/bundle/` rule rather than broad `vendor/`.
- Return every ecosystem with the repository-relative marker path or paths that caused detection, while retaining the existing ecosystem-name list for compatibility.
- Enumerate tracked paths through Git, inspect filename and size metadata only, and create exact-path recommendations for large, database, archive, generated, binary, or otherwise ambiguous candidates.
- Emit a separate high-severity warning for tracked secret-like filenames, with rotation/removal guidance and an explanation that `.gitignore` does not untrack or remove history.
- Preserve all existing transactional, path-containment, managed-block, configuration, hook, matching, and user-rule precedence guarantees.
- Regroup text output into planned changes, conflicts, warnings, and recommendations; extend JSON additively with stable schema/version and diagnostic fields.
- Prominently surface the Git consequences of adding an unmanaged `.gitattributes` policy to an established repository before `--apply` writes it.
- Replace the root README with tested installation, audit, apply, check, upgrade, safety, reporting, policy, platform, and scenario documentation covering features 0001-0005.

### Out of scope

- Reading candidate file contents, entropy analysis, comprehensive secret detection, or claiming parity with a dedicated secret scanner.
- Automatically adding a recommendation to `.agentsignore`, deleting or untracking a file, rotating credentials, rewriting Git history, or failing a run solely because warnings or recommendations exist.
- Changing `.agentsignore` matching semantics, `warn`/`deny`/`off` decisions, hook coverage, client trust behavior, or the Python-standard-library-only runtime.
- Adding ignore adapters for other products, dependency installation, packaging infrastructure, CI workflow files, release automation, or deployment.
- Treating `.gitignore`, `.gitattributes`, `.agentsignore`, native denies, or lifecycle hooks as a complete sandbox or security boundary.

## Assumptions and decisions

- **D-1 — Feature 0004 is the implementation base.** GitHub PR 4 is merged and local `main` matches `origin/main` at `971518e`. The plan assumes committed Claude project settings, conservative native denies, root-safe hooks, validation, `Change.treatment`, and `Change.integration` from feature 0004 are available and must remain compatible.
- **D-2 — Default rules become data, not independent string literals.** Introduce one classified rule-group model consumed by `.gitignore`, `.agentsignore`, report rendering, and documentation tests. A group records target, classification (`high-confidence` or `ecosystem-specific`), reason, rules, optional ecosystem, and detection markers. Keep target-specific differences explicit; do not force `.gitignore` and `.agentsignore` to have identical bodies.
- **D-3 — The no-ecosystem `.agentsignore` policy is intentionally minimal.** Its managed block retains `.git/`, personal/local agent files, Shrinkydink's local runtime cache, `.env`/`.env.*` with the existing example/sample/template negations, and the existing private-key/certificate extensions. Generic `vendor/`, `build/`, `out/`, `*.db`, `*.sqlite*`, archives, `*.map`, `*.jar`, `*.war`, compiled-library/executable extensions, and `*.bin` are not universal defaults. This favors false negatives and prevents fixtures or checked-in distribution assets from disappearing from agent context.
- **D-4 — Existing ecosystem coverage is preserved and made explainable.** Retain the current Node, Python, Rust, Go, Java, .NET, Ruby, Terraform, and Swift marker catalog and bounded depth/pruning behavior. Return all matching relative marker paths in deterministic order. Reuse the current ecosystem-specific `.gitignore` groups as the starting policy for `.agentsignore`, narrowing imprecise entries: broad `build/` is allowed only for Node, Python, and Java; `*.map` only for Node; `*.class`, `*.jar`, and `*.war` only for Java; `vendor/bundle/` only for Ruby; and no ecosystem automatically owns generic `out/`, database, archive, or `*.bin` rules.
- **D-5 — Recommendations are exact, reviewable, and non-mutating.** Replace `tracked_large_files` with a tracked-path metadata collector based on NUL-delimited `git ls-files` plus `lstat`/size metadata; classification uses only the path string and metadata. Emit at most one recommendation per path with deterministic categories/reasons, `size_bytes` when available, the configured agent-ignore target, and a root-anchored, Git-ignore-escaped exact-path `suggested_rule`. Multiple findings for one path are combined rather than suggesting a broad extension or directory rule. Recommendations do not enter `changes` or `apply_changes` and do not affect exit codes.
- **D-6 — Secret-like filenames get both recommendation and warning treatment.** Share a conservative filename policy with the generated secret defaults: `.env` and `.env.*` except documented example/sample/template variants, plus `.pem`, `.key`, `.p12`, and `.pfx`. A tracked match receives a recommendation and a `high` severity warning. The warning states that `.gitignore` does not untrack the file, advises removing the credential from the repository/history as appropriate and rotating it, and never opens, hashes, samples, or prints file content. Do not infer secrets from entropy or broad names such as arbitrary `credentials.json` in this feature.
- **D-7 — JSON evolution is additive and explicitly versioned.** Add `report_version: 1`, `ecosystem_detections`, `default_rule_groups`, `conflicts`, and `recommendations`. Retain existing `repo`, `mode`, `ecosystems`, `settings`, `changes`, `warnings`, change objects, modes, and exit codes. Keep conflicts in `changes` for old consumers and duplicate their stable report projection in `conflicts`. Add `severity` to warnings while preserving `kind` and `message`. Text output groups create/update entries under Planned changes, conflict entries under Conflicts, then Warnings and Recommendations; unchanged entries remain available without being mislabeled as planned work.
- **D-8 — Established `.gitattributes` changes require prominent review, not a new policy flag.** Treat a non-empty existing `.gitattributes` without Shrinkydink markers as established user configuration. Audit/check continue to show the exact proposed managed block, but also emit a dedicated policy warning explaining that attributes control Git normalization/diff behavior, not LLM access, and that later staging may renormalize files. `--apply` remains the explicit approval boundary. Existing managed blocks update normally, later user rules retain precedence, and no `--no-gitattributes` or new config key is added in this brief.
- **D-9 — Managed-block upgrades remove old broad defaults but never user rules.** The next audit will visibly propose a narrower Shrinkydink-owned `.agentsignore` block. Rules outside the markers remain byte-preserved and retain last-rule precedence. Detect legacy managed broad defaults and add an upgrade warning that names the policy transition without automatically copying those rules into user-owned space. Keep `.shrinkydink.json` at schema version 1 because its shape is unchanged; document the policy change as an upgrade, not a configuration migration.
- **D-10 — Documentation examples are executable contracts.** Add a small versioned, synthetic documentation/diagnostic fixture manifest and tests that assert each canonical command is present in the README and exercise its argv against temporary repositories. Cover a new repository, an established repository with user-owned ignore/attribute rules, and a repository with an intentionally tracked large fixture that the user elects to keep. "Upgrade" means audit the new policy diff, review recommendations, apply explicitly, and run check; there is no invented upgrade subcommand.
- **D-11 — Python 3.9 and standard-library-only support remains load-bearing.** Use dataclasses, `pathlib`, `stat`, `subprocess`, `json`, and existing unittest patterns only. Do not add a package manifest: this repository deliberately has no ecosystem marker, and adding one would alter its own generated defaults and dogfood check.
- **D-12 — Preserve the reconciled worktree.** Planning occurs on clean tracked `main` with only `.agents/skills/feat`, `.claude/skills/feat`, and the feature-0005 brief untracked. No feature-0005 branch or pull request exists. `run` must branch from current remote `main`, carry the brief and this plan as related work, and leave the local skill links untouched and uncommitted.

## Planning-time implementation findings

- `scripts/shrinkydink.py::detect_ecosystems` currently returns only `set[str]`, so the CLI cannot explain which filename triggered detection. Its marker tables and bounded walk are the correct place to produce deterministic detection records.
- `gitignore_body` is already ecosystem-aware, but `agentsignore_body` hard-codes most dependencies, caches, build trees, archives, databases, and compiled formats for every repository and adds only Terraform conditionally. The two renderers need classified shared policy data rather than another conditional patch.
- `tracked_large_files` already uses `git ls-files -z` and filesystem size metadata without opening candidates, but collapses all matches into one warning string, samples only eight paths, and exposes no copyable action or stable JSON object.
- `WarningItem` has only `kind` and `message`; `Change` already has additive `treatment` and `integration`. The JSON payload exposes `changes` and `warnings`, while conflicts are represented only by `change.status == "conflict"` and recommendations do not exist.
- `print_text_report` currently interleaves OK, create/update, and conflict entries before a generic warning section. It needs a presentation-only regrouping that leaves apply/check exit semantics and the underlying change list unchanged.
- `merge_managed_block` prepends the owned block and preserves later user content, which already gives `.gitignore`, `.gitattributes`, and `.agentsignore` user rules final precedence. Existing preservation, symlink, preflight, rollback, and local-content suppression tests should be extended rather than reimplemented.
- `gitattributes_body` proposes broad line-ending normalization and binary attributes for every repository. An audit diff is visible today, but no dedicated warning distinguishes Git normalization from agent access or explains the staging impact for existing unmanaged configuration.
- The root `README.md` is nine lines, contains misspellings, refers to a "gentsignore" file and `.gitattribute`, and omits the CLI, transaction model, matching contract, report schema, client integration, limitations, upgrade behavior, and all three required scenarios. The reference documents contain most authoritative detail and should be linked rather than duplicated inconsistently.
- The current suite has 43 standard-library tests across transaction, guard, conformance, and integration behavior. There is no dedicated tracked-file diagnostic or documentation-example test module. Existing verification convention is focused unittest modules, full discovery, dogfood `--check`, runtime asset comparisons, and `git diff --check`.

## Implementation steps

1. **Define stable policy and diagnostic models.** Add standard-library dataclasses/constants for ecosystem detections, classified rule groups, tracked-path metadata, recommendations, warning severity, report version, and shared terminology. Keep serialized field order and deterministic sorting explicit.
2. **Refactor ecosystem detection to retain evidence.** Return ecosystem names plus every matching repository-relative marker path from the existing bounded metadata walk. Preserve pruning and depth limits, and adapt callers without reading marker contents.
3. **Centralize ignore policy.** Replace independent hard-coded renderer lists with target-aware high-confidence and ecosystem-specific groups. Preserve the current `.gitignore` intent, narrow `.agentsignore` according to D-3/D-4, use group metadata in comments/reporting, and keep the configured ignore path in every generated note.
4. **Add upgrade and `.gitattributes` policy diagnostics.** Detect replacement of the legacy broad managed `.agentsignore` block and established unmanaged `.gitattributes`; emit prominent warnings while retaining exact proposed diffs, transactional application, and later user-rule precedence.
5. **Collect tracked path metadata safely.** Generalize `tracked_large_files` into a NUL-safe tracked-path collector that uses Git filenames and non-content size metadata, handles missing/unrepresentable paths conservatively, never follows candidate symlinks for classification, and returns no candidates when Git metadata is unavailable.
6. **Classify and aggregate recommendations.** Add conservative pure-path classifiers for large files, databases, archives/packages, source maps/minified/generated names, compiled/binary extensions, and ambiguous path components. Deduplicate per path, combine reasons/categories, render an exact anchored escaped rule, and never feed recommendations into the write transaction.
7. **Add tracked-secret warnings.** Apply the D-6 allowlist, create one high-severity warning per tracked match with rotation/untracking/history guidance, and guarantee output includes only the path, metadata, policy reason, and suggested action—not candidate bytes.
8. **Evolve reports compatibly.** Build one report payload used by JSON and text rendering; retain all legacy fields, add D-7 fields, separate text sections, preserve diff suppression/local-content suppression, and keep audit/check/apply return codes unchanged by warnings/recommendations.
9. **Add versioned diagnostic fixtures and focused tests.** Create synthetic scenario data under `tests/fixtures/diagnostics/v1/` and `tests/test_diagnostics.py`. Materialize temporary Git repositories with marker names and generated test bytes, verify no-content reads through targeted mocks/sentinels, cover exact escaping and ordering, and extend existing preservation/idempotence cases.
10. **Rewrite and test the root README.** Make it the concise user entry point: purpose and non-sandbox warning; installation; audit/apply/check; generated shared/local files; automatic defaults versus recommendations; JSON/CI behavior; safety/rollback; custom paths and exact matching; warn/deny limitations and bypasses; Claude/Codex/platform notes; the three required scenarios; upgrade procedure; verification; and links to detailed references.
11. **Synchronize packaged guidance and canonical references.** Update `SKILL.md`, `references/configuration.md`, `references/installation.md`, and `references/platform-support.md` for the narrowed policy, report schema, `.gitattributes` warning, recommendations, secret remediation, upgrade behavior, and consistent terminology. Keep `references/agentsignore.md` authoritative for syntax and change it only where default-policy examples need clarification.
12. **Add executable documentation coverage.** Create `tests/fixtures/documentation/v1/examples.json` and `tests/test_documentation.py` to verify the README contains each canonical command and to exercise audit/apply/check/upgrade argv against the three synthetic repository states without network or client dependencies.
13. **Regenerate dogfood policy and review scope.** Run normal Shrinkydink apply during `run` to update its managed `.agentsignore` block and any generated policy prose. Stage only intended feature files; preserve `.agents/skills/feat` and `.claude/skills/feat`; verify no product runtime helper changed unless the diagnostic design genuinely requires it.

## Risks and follow-ups

- **Narrower defaults reveal context on upgrade.** Files previously hidden only by Shrinkydink's managed broad rules may become visible after apply. The audit diff and upgrade warning are required; repositories that intentionally want a former rule must add it outside the managed block after review.
- **Filename classification is heuristic.** A `.db`, `.jar`, `.map`, or large file may be necessary source/test data, while a secret may use an innocuous name. Exact-path recommendations, non-blocking semantics, and explicit false-negative preference prevent the heuristic from silently hiding data but cannot make it comprehensive.
- **Tracked-secret warnings are not remediation.** Ignoring or untracking a file does not remove it from history, and rotating a credential may require provider-specific action. Documentation must avoid unsafe one-size-fits-all history-rewrite commands and point users toward their incident process.
- **Git metadata has edge cases.** Missing worktree files, submodules, symlinks, unusual encodings, and filenames containing newlines may make size or a line-oriented copyable rule unavailable. Keep NUL-safe enumeration, avoid following symlinks, expose unavailable metadata honestly, and never weaken transaction safety to handle a recommendation.
- **Duplicated conflict projections can drift.** `changes` remains authoritative for compatibility while `conflicts` is additive. Build both from the same objects/payload helper and test equality of the projected records.
- **Report growth affects CI consumers.** Additive fields and warning severity should be compatible, but strict consumers may reject unknown keys. Document `report_version`, retain prior keys and meanings, and call out the additive schema in upgrade notes.
- **`.gitattributes` can change later staging behavior.** Even a reviewed prepend may cause Git to renormalize files later. The dedicated warning and explicit `--apply` boundary are required, and user overrides after the managed block retain precedence.
- **Documentation can still drift from clients.** README examples are tested against Shrinkydink's CLI, not live Claude/Codex versions. Keep client-specific detail in the existing references and retain feature-0004's live-client/native-Windows pre-release smoke follow-up.
- **Policy tables can over-consolidate targets.** `.gitignore` controls untracked-file discovery, `.agentsignore` controls agent context, and Claude native denies are stronger and less expressive. Share classification data only where semantics match; do not translate arbitrary default or user rules into native denies.
